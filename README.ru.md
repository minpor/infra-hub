# Infra Hub

**Собирайте на своём железе. Разворачивайте на своих серверах.**

[English](README.md) · [Русский](README.ru.md) · [Установка](docs/self-hosting.ru.md) · [Участие](CONTRIBUTING.md) · [Лицензия MIT](LICENSE)

Infra Hub — платформа для самостоятельного размещения: панель сборки и деплоя собственных проектов на Linux-серверы. Исходники остаются в GitHub, сборки выполняются на вашем оборудовании, а готовый образ публикуется в registry и разворачивается по SSH с проверкой здоровья и сохранением результата.

ПО не требует подписки и покупки CI-минут. Оборудование, диски, сеть, домен и резервные копии обеспечивает владелец; у внешних сервисов могут быть свои тарифы.

> **Ранняя разработка / 0.1.** Это рабочий проект, который готовится к более широкому использованию. Текущая модель установки рассчитана на одного владельца. Сборкам репозиториев нужна отдельная настройка rootless Docker. Интерфейс пока русскоязычный; документация есть на английском и русском. Готовый облачный сервис, высокая доступность и универсальная совместимость с GitHub Actions не заявлены.

## Возможности

| Область | Что реализовано |
| --- | --- |
| Проекты | Ссылки на GitHub, поиск, история и фиксация точного commit |
| Очередь | Задания в PostgreSQL, идемпотентная постановка, lease исполнителя, отмена и обнаружение прерванных заданий |
| Сборки | Отдельный worker; одноразовые контейнеры Java 21 / Node.js в rootless Docker |
| Наблюдаемость | Сохранённые шаги, логи, коды завершения, статусы и настройки CPU/RAM |
| Образы | Упаковка одного исполняемого JAR собственным Dockerfile платформы, публикация и сохранение digest |
| Серверы | Отдельные SSH-ключи, подтверждение отпечатка и проверка SSH/Docker |
| Деплой | Передача образов по SSH, сверка содержимого, HTTP health check, история и поддерживаемый откат |
| Pipeline | Опрос веток, переход от сборки к деплою, ручной запуск и приостановка |
| Агенты | MCP с отзывными ключами и правами READ / RELEASE / CONFIGURE в пределах проектов |
| Пример | Встроенная проверка Java-проекта и отдельный статический прототип интерфейса |

Общая публикация поддерживает исполняемые JAR. Для существующих Compose-приложений есть расширенный адаптер с требованиями к структуре и проверкам здоровья. Подпись/публикация Android и некоторые вспомогательные команды пока **привязаны к Aukni**, а не являются универсальным мобильным CI. Подробности — [возможности и ограничения](docs/capabilities.md).

## Устройство

```text
Браузер / MCP-клиент
        │ HTTPS
      Caddy ── статический React-интерфейс
        │
   Kotlin / Spring Boot API ── GitHub OAuth + необязательный GitHub App
        │                      (архив точного commit)
    PostgreSQL
        │
   worker ── rootless Docker ── одноразовая сборка
        │                       (ограниченный proxy зависимостей)
     registry
        │ digest образа
   deployer ── SSH с закреплённым ключом ── целевой Docker-сервер
```

API, worker и deployer используют общую БД состояния. Код репозитория не получает Docker socket, пароль БД, OAuth, GitHub App или SSH-ключи. Доверенный worker управляет **отдельным rootless** Docker; deployer также имеет доступ к серверам выкладки. Это граница доверия установки одного владельца, а не изоляция для публичного сервиса выполнения чужого кода.

Одновременно выполняется одна тяжёлая сборка. Потеря lease приводит к `INTERRUPTED`, без ложного успеха и слепого повтора. Успешная сборка подтверждает артефакт; успешный деплой отдельно подтверждает проверку приложения.

## Локальный запуск

Потребуются Linux, **JDK 21** с `javac`/`jar`, **Node.js 22.12+**, npm и **PostgreSQL 16**. Локальную БД можно запустить через Docker Compose v2. Для управления серверами нужен OpenSSH client.

```bash
git clone https://github.com/minpor/infra-hub.git
cd infra-hub
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"

docker compose up -d --wait postgres
./gradlew :backend:bootJar
npm --prefix frontend ci
```

Укажите свой путь к JDK. Запустите три процесса в отдельных терминалах из корня репозитория:

```bash
# 1. API
java -jar backend/build/libs/infra-hub.jar
```

```bash
# 2. Worker
java -jar backend/build/libs/infra-hub.jar --spring.profiles.active=worker
```

```bash
# 3. Интерфейс
npm --prefix frontend run dev
```

Откройте [127.0.0.1:5173](http://127.0.0.1:5173), создайте проект **без репозитория** и запустите Java-пример. Он действительно компилирует, тестирует и упаковывает код; шаги и журнал сохраняются. Для сборок GitHub нужен [отдельный runner](docs/self-hosting.ru.md#runner-репозиториев-и-deployer).

Локальный профиль использует loopback и не требует входа. **Не открывайте его в сеть.** Публичная панель должна работать с production-профилем, HTTPS и проверкой владельца. Compose читает `.env`, отдельная JVM — нет: нестандартные настройки БД экспортируйте в окружение обоих Java-процессов.

Приложение останавливается Ctrl+C, БД — `docker compose stop`. Данные сохраняются в volume. `docker compose down -v` удаляет их.

## Развёртывание на сервере

[Русская инструкция](docs/self-hosting.ru.md) и [English guide](docs/self-hosting.md) описывают:

1. Сборку файлов релиза из исходников.
2. Настройку домена, GitHub OAuth и числового ID владельца.
3. Запуск панели, PostgreSQL и worker примера через Compose.
4. Подключение отдельного rootless runner, proxy зависимостей, registry и SSH deployer.
5. GitHub App для приватных репозиториев, публикацию первого JAR и деплой.
6. Резервное копирование, обновления, восстановление, лимиты и диагностику.

Начинайте с [`deploy/self-host/`](deploy/self-host/) и [`.env.example`](deploy/self-host/.env.example). Старые `deploy/enable-*.py`, `update-*.py` и `compose.live.yaml` — материалы обслуживания конкретной установки, **не установщик для новой машины**.

Панель собирается из исходников: готовые публичные Infra Hub images и установка одной командой пока не предоставляются. Новую Compose-конфигурацию нужно проверить в своём окружении перед использованием в production.

## Существенные ограничения

- Один заданный владелец GitHub; нет командных ролей, организаций и изоляции арендаторов.
- Исходники поступают архивом GitHub: без `.git`, Git LFS и содержимого submodules. Максимум архива — 32 MiB.
- Команда репозитория: до 40 минут, 512 процессов; tmpfs `/work` 4 GiB и `/tmp` 512 MiB входят в лимит RAM. Начальные настройки задания — 6 CPU / 16 GiB, меняются в панели. Это настройки сборок, а не минимальные требования панели.
- Сеть сборки ограничена HTTPS-списком хостов зависимостей. Дополнительные домены, приватные registry и toolchain настраивает оператор.
- Общая упаковка принимает один JAR до 256 MiB и не выполняет Dockerfile репозитория. Передача образа для деплоя — до 2 GiB.
- Нет автоматической очистки логов/образов, общего кеша зависимостей, PR statuses, release tags, движка GitHub Actions YAML, Kubernetes и HA-установки.
- Откат не отменяет миграции БД и внешние побочные эффекты. Прерванный деплой сверяется с тем же UUID.
- Значения runtime environment сохраняются в PostgreSQL **без шифрования на уровне приложения**. Защищайте БД, volumes и резервные копии.

## Разработка и проверки

```bash
npm --prefix frontend ci
(cd frontend && npx playwright install chromium)
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
./scripts/check.sh
python3 -m unittest discover -s scripts -p 'test_*.py'
```

Основная проверка создаёт временную PostgreSQL, запускает backend-тесты, сборку интерфейса, сценарии с настоящими API/worker и Playwright. Нужны серверные бинарники PostgreSQL (`initdb`, `pg_ctl`, `createdb`, `pg_config`), свободные локальные порты и пользователь без root. Можно задать `PG_BIN`, `HUB_TEST_DB_PORT`, `HUB_TEST_API_PORT`. Только JVM-проверки: `./scripts/check.sh --backend-only`.

Подробнее: [локальная разработка](docs/local-development.md), [участие в проекте](CONTRIBUTING.md), [безопасность](SECURITY.md). Проверки с обращением к существующим серверам запускаются отдельно и в локальный check не входят.
