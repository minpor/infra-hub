# Деплой через YAML

[English](deployment-yaml.md) · [Русский](deployment-yaml.ru.md) · [Примеры](../examples/deploy/) · [Схема для редактора](deployment.schema.json)

Сценарии деплоя принадлежат проекту и хранятся в Git. Можно подключить любое число файлов `.yaml` / `.yml`: `.infra-hub/dev.yaml`, `.infra-hub/production.yaml`, `.infra-hub/worker.yaml` и другие. У каждого проекта свои файлы. Несколько сценариев могут вести к одному приложению, но автоматический владелец выкладки у приложения один; остальные доступны для ручного выпуска.

Это версионируемый формат Infra Hub с именованными shell-шагами, независимый от прежних адаптеров конкретных приложений. YAML GitHub Actions/GitLab CI напрямую не исполняется.

## Как подключить

1. Создайте проект с GitHub-репозиторием и подключите сервер с подтверждённым SSH-ключом.
2. В «Приложениях» создайте приложение **YAML-сценарий по SSH**, выбрав проект и сервер. Подойдёт SSH-only сервер. Runtime environment задаётся в приложении; секреты в YAML не помещаются.
3. Закоммитьте YAML в репозиторий.
4. Нажмите **Подключить YAML**, выберите приложение, явную ветку/тег/SHA и путь файла. **Проверить YAML** загрузит его из точного commit и покажет содержимое.
5. Сохраните привязку. Автоматизация изначально выключена. **Запустить YAML-выпуск** явно выполнит сборку и деплой один раз. Автоматизацию новых commit включайте отдельно.

Preview не выполняет команды. Если ветка сдвинулась после preview, сохранение отклоняется. Каждый запуск сохраняет исходный YAML, hash, разобранный сценарий и commit SHA вместе со сборкой. Runtime environment фиксируется отдельно в закрытом поле БД деплоя. Повтор и откат используют сохранённую конфигурацию; изменения файла не меняют старые попытки. YAML-pipeline реагирует на полный новый SHA, без специальных имён проектов/веток/mobile-каталогов.

## Пример версии 1

```yaml
version: 1
name: Production service
build:
  steps:
    - name: Tests
      run: sh ./scripts/test.sh
      timeoutSeconds: 600
    - name: Package
      run: sh ./scripts/package.sh
      timeoutSeconds: 600
  # Необязательно: публикация executable JAR в образ по digest.
  # artifact: build/libs/service.jar

deploy:
  directory: /srv/my-service
  steps:
    - name: Apply release
      run: ./deploy.sh "$HUB_COMMIT_SHA"
      timeoutSeconds: 300
  verify:
    - name: Confirm version and health
      run: ./verify.sh "$HUB_COMMIT_SHA"
      timeoutSeconds: 60
  rollback:
    - name: Restore previous version
      run: ./rollback.sh
      timeoutSeconds: 300
```

Каталог `deploy.directory` должен существовать на целевой машине. Скрипты этого примера уже установлены там. Центр не копирует Git checkout в каталог неявно: сценарий сам делает fetch/checkout точного SHA либо использует доставленный образ. Git credentials и инструменты целевой машины настраивает владелец; GitHub App token центра не передаётся.

## Поля и лимиты

- `version`: целое `1`; `name`: название до 80 символов.
- `build.steps`: 1–20 именованных шагов `run`. Каждый — отдельный `sh -eu` из корня исходников в rootless sandbox. Файлы сохраняются между шагами; переменные shell и `cd` — нет. Сохраняются лимиты CPU/RAM, сети и toolchain runner.
- `build.artifact`: необязательный путь к executable JAR. При заполнении используется существующая публикация образа и доставка по digest. Без него платформа не требует Docker build/push/pull: успешная сборка исходников может выпускаться shell-командами.
- `deploy.directory`: абсолютный рабочий каталог приложения; `/` и traversal запрещены.
- `deploy.steps`: 1–20 команд на целевом сервере с правами выбранного SSH-пользователя.
- `deploy.verify`: 1–20 **идемпотентных проверок без изменений состояния**. Нулевой код должен подтверждать нужную версию и здоровье — проверяйте image ID/version endpoint, а не только открытый порт. Проверки повторяются при сверке.
- `deploy.rollback`: необязательные 1–20 шагов восстановления при ошибке начальной выкладки/проверки. Откат приложения и БД определяет проект.
- Шаг содержит `name`, `run`, необязательный `timeoutSeconds`: по умолчанию 300, допустимо 1–900. Сумма build — до 2400 секунд, deploy + verify + rollback — до 3600. Общий таймаут сборки по-прежнему 40 минут.

Файл — до 64 KiB, скомпилированный build-script — до 32000 символов. Неизвестные поля, повторяющиеся ключи, несколько документов, object tags, anchors/aliases, traversal и неверные типы отклоняются. В версии 1 нет includes, неявной подстановки переменных, матриц и параллельных jobs. Shell-подстановка выполняется только в соответствующем процессе.

## Runtime environment

Команды получают environment приложения и зарезервированные значения:

| Переменная | Содержимое |
| --- | --- |
| `HUB_COMMIT_SHA` | Точный commit |
| `HUB_APPLICATION_ID`, `HUB_BUILD_ID`, `HUB_DEPLOYMENT_ID` | Идентификаторы операции |
| `HUB_CONFIG_PATH`, `HUB_CONFIG_SHA256` | Путь и hash YAML |
| `HUB_IMAGE_ID`, `HUB_IMAGE_REFERENCE` | Проверенный image ID / digest или пустая строка без artifact |

Значения `HUB_` имеют приоритет при совпадении имён. SSH/GitHub/signing-ключи не выдаются скриптам. Environment и его snapshot сохраняются в БД без шифрования на уровне приложения; защищайте backups. Не печатайте секреты через `set -x`, `env` и журналы. Авторы YAML управляют командами выпуска с правами выбранного пользователя сервера — доступ к репозиторию является полномочием на выпуск.

## Ошибки и повтор

На сервере сохраняются квитанции и блокировка приложения. Успех означает завершение deploy и verify. Если после ошибки успешно выполнен настроенный rollback — статус FAILED. Без подтверждённого восстановления — INTERRUPTED, новый выпуск блокируется до сверки.

Повторяйте тот же UUID деплоя. Исполнитель проверяет оставшийся активный процесс и запускает только verify; deploy/rollback вслепую не повторяются. При необходимости вручную приведите цель к проверяемому состоянию и повторите сверку. Иной ввод не может переиспользовать квитанцию. Команды должны завершать работу в foreground: произвольные фоновые процессы и внешние эффекты не становятся транзакционными автоматически.

Отмена до удалённых эффектов может остановить подготовку. После начала bounded-сценарий завершается с фактическим результатом; отмена не обещает вернуть произвольные изменения. Ручной откат SCRIPT-приложения запускает прежний неизменяемый сценарий с прежним SHA/образом. Скрипты должны поддерживать такой выпуск. Для Android ограничения versionCode остаются ответственностью сценария; откат старого legacy Android по-прежнему запрещён.

## API и совместимость

- POST `/api/deployment-yaml/preview`: `{applicationId, ref, path}`.
- POST `/api/deployment-yaml`: `{id, applicationId, ref, path, expectedSha, enabled}`.
- POST `/api/pipelines/{id}/release`: `{requestId}` — явный YAML-выпуск.
- Старый `/run` при выключенной автоматизации остаётся preview-сборкой. `/enabled` управляет автоматизацией. MCP `hub_ensure_release` также использует YAML точного SHA.

Browser-запись требует owner session и CSRF. Сервер привязан к приложению; YAML не может выбрать другое SSH-подключение. YAML-сборка не разворачивается в другом приложении. У файлов независимая история; лимиты параллельности установки сохраняются.

V10 добавляет привязки и snapshots. Прежние Aukni/Java/Compose адаптеры совместимы. Подключение файла не отключает старую автоматизацию: при замене сначала приостановите её. Через обычные команды можно выпускать Compose с несколькими `-f`, systemd, статические сайты и собственные скрипты без добавления имени проекта в код платформы. Дополнительные build/target инструменты устанавливает оператор.

Примеры для адаптации: [Java-образ](../examples/deploy/java-image.yaml), [Compose production](../examples/deploy/compose-production.yaml), [systemd staging](../examples/deploy/systemd-staging.yaml). Они не являются готовыми релизами личных серверов автора.

## Просмотр, редактирование и кэш

В подключённой конфигурации доступны **Просмотр YAML** и **Редактировать YAML**. Переключение режимов сохраняет черновик; проверка YAML обязательна перед сохранением. Кнопка **Сохранить в ветку** создаёт коммит в репозитории. GitHub App нужен доступ **Contents: read and write**, а правила защиты ветки должны разрешать запись. Если ветка или файл изменились после открытия, сохранение отклоняется; черновик остаётся в редакторе. Теги и SHA доступны для просмотра; для записи нужна ветка. Если автоматизация включена, коммит может запустить выпуск. Содержимое YAML предыдущих сборок сохраняется и доступно в карточке сборки.

В **Настройки → Раннер** выберите проект и задайте его CPU, память и кэш. Проекты без собственных настроек наследуют общие. **Использовать общие настройки** возвращает наследование. В YAML можно указать `build.cache: true` или `build.cache: false`; без поля применяется настройка проекта.

Кэш включён по умолчанию. У каждого проекта отдельный постоянный Docker volume: Gradle, зависимости и npm-кэш сохраняются между запусками. Выключение подключает только временные каталоги, а прежний кэш остаётся до повторного включения. Карточка сборки показывает фактические CPU/RAM, состояние кэша и имя хранилища. Статус заполненного хранилища означает доступность файлов; пригодность конкретных зависимостей проверяют Gradle/npm. Нужно обновить worker и builder вместе; объём кэша на диске не ограничивается автоматически. Подробности: [настройки раннера](runner-settings.md).

## Выбор окружения и ветки в проекте

Кнопка «Открыть проект» сначала показывает вкладку «Настройки и скрипты»: здесь доступны YAML и исходники выбранного сценария. Вкладка «Запуск» открывает выбор: только сборка, DEV или PROD. Ветки загружаются из GitHub; доступны дополнительные страницы и ручной ввод. Для выкладки нужно выбрать сценарий с совпадающими окружением и веткой. Перед запуском показаны приложение и сервер назначения; команды и YAML находятся в дополнительных настройках.

Метка `environment` задаётся явно при подключении YAML или в настройках сценария в «Приложениях»: `dev`, `prod` либо без окружения. Существующее явное `configuration.target` приложения сохраняется, остальные сценарии нужно распределить самостоятельно. Имена веток и приложений не определяют окружение. Смена метки не меняет сервер, ветку или переменные приложения.

Разовый выпуск доступен и для приостановленного сценария: сборка, выкладка и проверка выполняются без включения будущих автоматических выпусков. Результаты сборки и деплоя учитываются отдельно.

Если сценарий пока настроен непосредственно в Infra Hub, вместо несуществующего репозиторного YAML показывается подписанное представление действующих настроек в YAML. В нём видны команда сборки, артефакт, ресурсы, сервер и параметры выкладки. Слева доступны полные исходники скриптов сборки и деплоя, а также используемые файлы репозитория, например `.github/workflows/ci.yml`. Открытие файлов не запускает сборку или деплой; значения переменных окружения не выводятся.
